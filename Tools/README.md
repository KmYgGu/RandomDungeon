# 검증 환경 (Unity 없이 돌리는 컴파일 + 테스트)

Unity 에디터를 켜지 않고 게임 코드를 컴파일하고, 순수 계산 부분을 실제로
돌려 보는 곳이다. **코드를 고쳤으면 여기부터 돌린다.**

## 돌리는 법

```bash
dotnet run --project Tools/Verify/Verify.csproj
```

이 한 줄이 게임 소스 컴파일(`Check`)까지 함께 한다. 마지막 줄이 `ALL PASS` 여야 한다.

컴파일 결과만 보고 싶으면:

```bash
dotnet build Tools/Check/Check.csproj --no-incremental
```

**에러 0 / 경고 0 이 기준선이다.** 경고가 하나라도 늘었으면 그건 내가 늘린 것이다.

## 무엇이 들어 있나

| | |
|---|---|
| `Check/Check.csproj` | `Assets/Code/**` 와 `Assets/RCode/**` 의 `.cs` 를 전부 컴파일한다. 게임을 빌드하는 게 아니라 문법·형 오류만 잡는다. 게임 코드가 물려받는 2d-extras 의 `Runtime/**` 도 함께 넣는다(`SiblingRuleTile` 이 `RuleTile` 을 상속한다). |
| `Verify/Verify.csproj` | 위에서 나온 `Check.dll` 을 참조해 실제 클래스를 직접 호출한다. |
| `Verify/Program.cs` | 테스트 본문. |
| `Common.props` | 두 프로젝트가 함께 쓰는 경로 설정. |

마지막 것은 특히 **에디터에서는 절대 드러나지 않는** 종류다. 판 단위 상태를
`static` 으로 들고 있는데, 에디터는 Play 를 누를 때마다 도메인을 다시 로드해
저절로 초기화해 주기 때문이다. 빌드에서는 그런 일이 없다. 그래서 에디터가 아닌
이곳에서 확인한다.

## 여기서 확인할 수 없는 것

Unity 런타임이 있어야 하는 것은 손대지 않는다.

- MonoBehaviour 의 생명주기(`Awake`/`Start`/`Update`)
- 코루틴, `WaitForSeconds`
- 씬 로드, `Destroy`, `DontDestroyOnLoad`
- `Tilemap`, 프리팹, Inspector 연결

즉 **`ALL PASS` 는 "에디터에서 잘 돈다" 는 뜻이 아니다.** 반대로 여기서
실패하면 확실히 잘못된 것이다. 실제 플레이 확인은 사람이 해야 한다.

## 테스트를 새로 넣을 때

`Verify/Program.cs` 의 `Main()` 에 호출 한 줄을 더하고 메서드를 쓴다.
판정은 `Check(조건, "실패했을 때 보여 줄 말")` 하나뿐이다.

**넣은 테스트는 반드시 한 번 실패시켜 봐야 한다.** 고친 코드를 잠깐 되돌리거나
기대값을 일부러 틀리게 해서 `FAILURES` 가 뜨는 걸 확인한 다음 되돌린다.
이걸 안 하면 아무것도 검사하지 않는 테스트가 조용히 통과만 하고 있게 된다.
상태를 더럽혀 놓고 시작하는 테스트라면, 더럽히기가 실제로 먹혔는지도
함께 검사해 둔다(`준비 실패: ...` 로 시작하는 줄들이 그것이다).

## 환경

- **.NET SDK** 가 필요하다(`dotnet --version`).
- **Unity 2020.3.21f1** 설치 경로를 참조한다. 버전이나 위치가 다르면
  `Common.props` 의 `UnityVersion` 을 바꾸거나 명령줄에서 덮어쓴다:

  ```bash
  dotnet run --project Tools/Verify/Verify.csproj -p:UnityManaged="D:/Unity/2021.3.0f1/Editor/Data/Managed/UnityEngine"
  ```

- TextMeshPro 와 uGUI 는 `Library/ScriptAssemblies/` 에서 가져온다.
  `Library/` 는 git 에 올라가지 않으므로, **저장소를 새로 받았다면 Unity 로
  프로젝트를 한 번 열어야** 이 폴더가 생기고 빌드가 된다.

## 왜 `Assets/` 밖에 있나

Unity 는 `Assets/` 아래의 모든 `.cs` 를 게임 코드로 컴파일하려 든다.
여기 있는 `Program.cs` 는 `Main()` 을 가진 콘솔 프로그램이라 그 안에 두면
게임 빌드가 깨진다. 그래서 프로젝트 루트의 `Tools/` 에 있다.

`.gitignore` 에도 손을 대 두었다. Unity 용 `.gitignore` 는 `*.csproj` 를 통째로
무시하는데(에디터가 자동 생성하는 것들 때문이다), 그러면 여기 것도 함께 사라진다.
`!Tools/**/*.csproj` 로 되살려 두었으니 **그 줄을 지우지 말 것.**

## 던전 생성 추가 검증 (2026-10-18)

현재 `Verify`는 46개 검사 묶음이다. 기존 목록 이후에 도감·기록·적 수 상한·최종 지형 경로 검사가 추가되었다.

에디터용 던전 검사 코드도 Unity를 실행하지 않고 컴파일할 수 있다:

```powershell
dotnet build Tools/EditorCheck/EditorCheck.csproj --no-incremental
```

실제 타일맵·프리팹 검사는 Unity를 닫고 다음 배치 명령으로 실행한다. 씬은 저장하지 않는다.

```powershell
& 'C:/Program Files/Unity/Hub/Editor/2020.3.21f1/Editor/Unity.exe' -batchmode -nographics -projectPath "$PWD" -executeMethod DungeonGenerationVerification.Run -logFile "$PWD/Logs/dungeon-verify.log"
```

로그의 `DUNGEON VERIFY PASS`가 성공 기준이다. **종료 코드 0만으로 성공으로 판단하지 않는다:** 라이선스 오류 때도 Unity가 0으로 종료할 수 있다.
2026-10-18 실행은 기기 정보와 라이선스 불일치로 검사 시작 전 종료됐다. 플레이 모드에서 이동·전투·층 전환을 직접 확인하는 작업도 남아 있다.
통로 다양화 후 총 47종이다. `통로 모양과 연결 다양성` 검사는 실제 `CorridorRouting.Plan`과 문 선택을 사용해 모양 편중·경계/방 침범·재현성·밀집 배치의 연결을 확인한다. `DUNGEON_PREVIEW` 환경변수에 SVG 출력 경로를 지정하면 선택된 네 모양의 예시를 추가로 내보낸다. 이 예시는 후처리 전 경로이며 Unity 플레이 화면이 아니다.
입구 폭 보호 추가 후 총 48종. 문 칸과 바로 바깥 칸의 양옆을 네 방향에서 검사하며, 실제 연결 선택을 사용한 300개 배치에서 입구 폭과 연결성을 함께 검증한다. 보호 규칙을 제거했을 때 실패함을 확인했다.

카메라 검사: 중앙 고정 걷기의 표시 진행률(시작/중간/완료), 즉시 이동, 0초, 프레임 속도별 도착 검사. 즉시 이동 회귀 시 2개 실패를 확인했다. 실제 카메라/Sprite 동기화와 렌더링은 Unity 플레이 검증 대상이다.

UI 카메라 분리 검증: Unity 배치 모드의 -executeMethod UiCameraVerification.Run.
완료 표식은 UI_CAMERA_VERIFICATION_PASS이며 프로세스 종료 코드만으로 성공 판정하지 않는다.
게임 카메라를 소수 좌표/한 칸/먼 거리로 이동하며 HUD와 미니맵의 화면 좌표 불변, 지도 메시 생성 및 층 갱신을 검사한다.
현재 환경에서는 Unity 라이선스 machine binding 오류로 이 검증이 실행되지 않았고, 컴파일만 통과했다.

미니맵은 타일 스프라이트 대신 MinimapContours가 열린 칸의 합집합 외곽만 생성하고 UI에서 단색 1픽셀 선으로 그린다.
검사는 3x3 전체 512배치, 직선 병합, 오목한 모서리, 내부 구멍, 중복 칸을 포함한다.

미니맵 기호 검사: 여섯 종류의 지정 RGB 색과 모양(원/채운 네모/X/빈 네모), 대칭, 외곽 범위, 계단 내부 투명 여부.
계단을 채워 아이템과 같아지는 회귀를 넣었을 때 10개 검사가 실패함을 확인했다.

미니맵 탐색 검사: 시작 방/출입구만 표시, 통로 앞 한 칸, 방향 전환, 방 실제 입장 시 전체 표시, 기억 유지, 새 층 초기화, 워프, 벽과 대각선 제한.
입장 전 다른 방의 내부를 미리 공개하도록 바꾸면 해당 검사가 실패함을 확인했다.

미니맵 경계/적 시야 검사: 미탐색 바닥에 가짜 끝선을 만들지 않음(네 방향 및 2x2의 81조합), 실제 막다른 끝 보존, 같은 방 또는 눈앞 한 칸의 적만 표시.
탐색 여부와 현재 적 시야는 별도이다. 열린 끝을 막고 적을 무조건 표시하는 회귀를 넣으면 8개 검사가 실패한다.

현재 통로 탐색/근거리 적 시야는 바라보는 방향과 무관한 주변 8칸이다.
5x5 검사 영역에서 중심 주변 3x3만 탐색되는지, 적 역시 인접 8칸만 보이는지 검사한다. 같은 방 전체 적 표시와 대각선 벽 제한은 유지한다.
